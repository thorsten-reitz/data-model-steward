# Review of partner XSD `observations.xsd` (v2.1)

Severity: **High** = can corrupt or misinterpret data / blocks a sound API; **Medium** = needs a decision before go-live; **Low** = cleanup.
"Decision" = what the canonical model currently does (`model/airquality.model.yaml`). Every decision is reversible in that one file.

| ID | Severity | Element(s) | Finding | Decision in canonical model | Question for partners |
|----|----------|------------|---------|-----------------------------|-----------------------|
| I-08 | High | `observation/begin`, `end` | `xs:dateTime` makes the timezone **optional**. `2026-11-22T00:00:00` could be UTC or local time, and in local time the DST autumn hour happens twice. This is the biggest data-quality risk. | Canonical timestamps **must** carry an offset (`Z` or `+hh:mm`). JSON Schema enforces it with a `pattern`, because `format: date-time` is only an annotation by default in draft 2020-12. The strict XSD enforces it too. The compat XSD accepts offset-less values, so ingest must reject them or apply a configured per-partner timezone. | Which timezone do partners use? Can we make the offset mandatory in v2.2? |
| I-11 | High | `validity`, `verification` | Plain `xs:int` with no code list. Any integer is valid, and the meaning is undocumented. | **Assumed** EEA e-Reporting vocabularies: validity {-99, -1, 1, 2, 3}, verification {1, 2, 3}. Enforced in JSON and the strict XSD. Ingest must quarantine unknown codes. | Confirm the code lists. Are any partner-specific codes in use? |
| I-07 | High | `sampling/pollutant` | Free `xs:string`. The annotation says "EEA pollutant vocabulary", but EEA identifies pollutants by URI or numeric id (for example `.../pollutant/8` = NO2), and notations vary (`PM2.5` vs `PM25`). Nothing says which 6 pollutants are in use. | String of 1-32 chars, no enum yet. **Recommended**: an enum of the 6 notation codes, mapped to EEA URIs, once confirmed. | Which 6 pollutants, and the exact spelling of each? |
| I-01 | High | `station/@id`, `sampling/@id` | `xs:ID` has three consequences. (a) The value must be an NCName: it can't start with a digit and can't contain `:` or spaces, so a raw code like `0001` is invalid. (b) Stations and sampling points **share one ID space**, so a station and a sampling point can't have the same id. (c) Uniqueness holds **only within one document**: nothing guarantees the id is stable across deliveries, yet the API needs stable ids. | Treated as stable technical ids (to be confirmed). The JSON pattern `^[A-Za-z_][A-Za-z0-9._-]*$` (ASCII subset of NCName) guarantees round-trip to XML. | Are ids persistent across deliveries? Are they globally unique or only unique per partner? |
| I-14 | High | overall structure | One nested document carries station metadata and all observations. Volume: 400 stations x 6 pollutants x 24 h = **57,600 observations per day, about 21 M per year**. A daily file is about 10 MB of XML. The format has no correction or delta semantics: when a value is re-verified (verification 3 -> 1), the partner re-sends it with no marker. `observation` has `minOccurs=0`, so metadata-only deliveries are possible. | The XML/collection shape is only the **bulk ingest** format. The REST API exposes a flat `ObservationRecord` (paged and filtered by station, pollutant and time) and a `StationSummary` without observations. Re-sent observations are upserted on the key (samplingPointId, begin). | Do partners re-send corrected values? Full day or deltas? |
| I-12 | Medium | `observation` | No rule that `end > begin`, no fixed interval length ("hourly" isn't stated), inclusive/exclusive bounds aren't defined, no aggregation method (mean?), and no uniqueness of `begin` within a sampling point. | Interval read as [begin, end), hourly mean expected. The strict XSD adds `xs:unique` on `begin` per sampling point. `end > begin` and the 1 h length can't be expressed in XSD 1.0 or JSON Schema, so they must be checked in code. | Are all values hourly means? Any other averaging periods? |
| I-13 | Medium | `observation/value` | Required but nillable (fine: an explicit "no value"). But `xs:double` also accepts `NaN`, `INF` and `-INF`, which JSON can't represent. The XSD doesn't say how nil relates to validity (e.g. nil with validity=1?) or what the value means for below-detection-limit codes 2 and 3. Negative values are allowed. They can legitimately come from instrument noise, so they aren't forbidden. | `number | null`. Ingest maps NaN/INF to `null` plus validity -1 (proposal) and flags nil-with-valid combinations. | Is NaN/INF ever sent? Should nil be allowed with validity 1? |
| I-10 | Medium | `sampling/unit` | Free string, so `µg/m3`, `ug/m3`, `µg/m³` and `microgram/m3` are all valid. The `µ` character also brings encoding risk. CO is usually in mg/m3. | String with length limits. **Recommended**: a controlled list (EEA concentration vocabulary or UCUM, e.g. `ug/m3`, `mg/m3`) with normalisation at ingest. | Which unit strings do partners actually send? |
| I-02 | Medium | `station/@id` vs `stationCode` | Two station identifiers with unclear roles, and nothing makes `stationCode` unique. | `id` = technical key, `stationCode` = business key. The strict XSD adds `xs:unique` on `stationCode`. | Which one is the authoritative key? |
| I-04 | Medium | `position/lat`, `lon` | No range, no CRS or datum, unbounded precision. Also, `xs:decimal` becomes a JSON number (binary float), which is harmless at coordinate precision. | WGS84 decimal degrees **assumed**. Ranges [-90, 90] and [-180, 180] enforced in JSON and the strict XSD. | Confirm the CRS. |
| I-05 | Medium | `position/altitude` | `minOccurs=0` **and** `nillable="true"` give two ways to say "unknown". No unit or vertical datum. | Both forms mean unknown. JSON allows the property to be absent or `null`. Metres above mean sea level **assumed**. | Confirm the unit and datum. Pick one representation for unknown. |
| I-15 | Medium | `ObservationCollection` | No delivery metadata: no sender or partner id, generation time, reporting period or schema version in the instance. At least one station is required. | Not modelled (the API takes sender identity from authentication). **Recommended**: add `@provider`, `@generated` and `@schemaVersion` in v2.2. | Is the sender identifiable from the transport? |
| I-03 | Medium | `targetNamespace` | The version is in the namespace (`.../airquality/2.1`). A minor 2.2 change means a new namespace and breaks every consumer that matches on it. | Kept for compatibility. Recommend a stable namespace plus a `version` attribute in the future. | - |
| I-06 | Low | `stationType` / `StationKindType` | Confusing naming: the complex type for a *station* is `StationType`, while the *element* `stationType` uses `StationKindType`. Only the EEA *station type* is captured. The EEA *area* classification (urban/suburban/rural) is missing, and without it a "background" station is of limited use for analysis. Values are case-sensitive. | Canonical enum `StationKind`, with the XML names preserved. | Is area classification available? |
| I-09 | Low | `sampling` | Nothing restricts the number of sampling points per pollutant per station. Several are legitimate in EEA (parallel instruments), but an API query for "NO2 at station X" then needs a rule. Also `sampling` has `minOccurs=1`, so a station with no sampling point can't be sent. | Not restricted. The API filters by pollutant and returns every matching sampling point. | Is one sampling point per pollutant per station guaranteed? |
| I-16 | Low | `operator`, `name` | `operator` is free text, not an identifier. `name` has no language tag. | Strings, as given. | - |

## What can't be expressed in schemas (implement in ingest / API code)
- `end > begin`, and `end - begin = 1 h` (I-12)
- Offset-less timestamps from partners: reject, or apply a configured per-partner timezone (I-08)
- Unknown validity or verification codes: quarantine (I-11)
- NaN/INF to `null` (I-13)
- Unit normalisation (I-10)
- Upsert key (samplingPointId, begin) for re-sent or corrected values (I-14)
