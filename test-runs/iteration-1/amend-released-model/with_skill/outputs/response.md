I've worked CR-7 into the model as **version 1.1.0, a minor release with no breaking changes**. Nothing is renamed, retyped, made mandatory or removed, so your ~2 million existing permits stay valid. The three partners can stay on 1.0.0 for now, as long as one condition about the JSON they receive is met (explained below). I prepared 1.1.0 but **did not release it**: it is in `datamodel/model.yaml` with `status: draft`, and `releases/1.0.0/` is untouched.

## What I did with each CR-7 item

| # | Request | What I did | Why |
|---|---------|------------|-----|
| 1 | Rename `reference` to `fileNumber` | **Kept the name `reference`** and made "file number" the official business term: in the description, the glossary and the database comment. Use it in screens for the clerks. | The meaning doesn't change (1.0.0 already defined it as the file number). A rename breaks all three partners and the database. Carrying a second `fileNumber` field would just duplicate a mandatory value and still break the partners' strict validation. (D-004) |
| 2 | Every permit must have an applicant | Added `Applicant` (name, optional organisation, address) to `Permit` as **optional and nullable**. The rule "every permit recorded from 1.1.0 on needs an applicant" is written down as C-002, but the schemas don't enforce it. | Old permits have no known applicant, so making it mandatory would invalidate existing data and break the partners. (D-005) |
| 3 | New status "expired" | **Did not add it as a status value.** "Expired" is calculated: a granted permit whose validity end has passed. The new database view `permit_with_expiry` provides `expired` and `effective_status`. | Partners reject unknown status values, so the first expired permit sent to them would fail. A stored status would also need a nightly job to change statuses, and that hides whether the permit had been granted. (D-006) |
| 4 | `validUntil` with a time of day | Added a new field `validUntilDateTime` (with time zone offset). `validUntil` is marked as deprecated but still filled with the date. | Changing the type of `validUntil` would break data and partners. (D-007) |
| 5 | Category for conditions | Added the code list `ConditionCategory` (environmental, safety, other), optional on `PermitCondition`. The list is **extensible**, so the permits team can add categories later without breaking anyone. | Existing conditions have no category. (D-008) |
| 6 | Drop `keywords` | **Marked as deprecated**, not removed. Stop filling it. | Removing it is breaking. Deleting it is planned for the next major version. (D-009) |

`dmtool diff` still lists two new rules (C-002 and C-003) as "breaking". That's a cautious default in the tool. Neither rule can make existing data invalid: C-002 only applies to new permits, and C-003 only checks the new date-time field. I've noted why in D-003.

## The one exchange catch you need to know about

Partners validate strictly and reject any field they don't know (D-002). That means **any** new field breaks them, even an optional one. I checked this with the JSON Schema validator:
- A complete 1.1.0 document **fails** the 1.0.0 schema.
- The same document without `applicant`, `validUntilDateTime` and the conditions' `category` **passes** both schemas.

So until a partner moves to 1.1.0, the systems sending them data must leave those three fields out (D-010). Both example documents are in `exports/1.1.0/examples/`.
